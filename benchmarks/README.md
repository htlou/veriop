# Pinned benchmark workspace

The [target manifest](targets.tsv) pins all 25 requested upstream repositories. Run `python3 benchmarks/bootstrap.py --check` from the project root to check every pin. Source `benchmarks/env.sh` before using the locally installed toolchains. A fresh bootstrap clones the branch and checks out the exact manifest SHA if the branch has advanced.

The native benchmark gate uses each project's own benchmark command and metric. The short runs in `logs/` only confirm that an entry point works; their numbers are **not** baseline scores or optimization results. A checker smoke test confirms the verifier works, but is not a proof about a target optimization. A target is benchmark-ready only after its native benchmark and target-specific checker path both pass.

`bash benchmarks/run_zstd_alive2.sh` compiles wrappers around the pinned `ZSTD_count{Leading,Trailing}Zeros32_{fallback,default}` helpers at Clang 20 `-O1`, then checks each pair with bidirectional Alive2. Both functions require a nonzero operand in the upstream header; the wrappers encode that same precondition with `__builtin_assume`. The fallback and builtin LLVM bodies differ (table lookup versus `ctlz`/`cttz`). The script requires Alive2's explicit equivalence verdict because this `alive-tv` mode can exit zero even after a counterexample; `logs/zstd-alive2-negative.log` records an injected `+1` variant correctly rejected at input 1. This proves only these 32-bit helper alternatives under the stated precondition, not the full zstd compressor/decompressor or any measured performance gain.

`bash benchmarks/run_fast_float_alive2.sh` verifies two more pinned-source alternatives: `leading_zeroes_generic` vs runtime `leading_zeroes` for every nonzero 64-bit input, and `countr_zero_generic_32` vs runtime `countr_zero_32` for every 32-bit input, including zero. Clang 20 `-O1` preserves distinct generic and builtin IR. An injected `+1` in the leading-zero builtin wrapper is rejected (`logs/fast-float-alive2-negative.log`). A direct [eight-digit packed parser attempt](alive2/fast_float_eight_digit_attempt.cpp) against a scalar per-digit formula timed out under a 30-second Alive2 query budget (`logs/fast-float-eight-digit-timeout.log`); no claim is made for that parser kernel or the complete `from_chars` API.

`bash benchmarks/run_simdjson_alive2.sh` checks the pinned `fallback::numberparsing::parse_eight_digits_unrolled` against its Westmere SIMD counterpart. The input is a readable 16-byte array because Westmere loads 16 bytes; the first eight must be ASCII digits. Clang 20 `-O2` generates distinct SWAR and SSSE3/SSE4.1 IR. The script saves raw and checked IR, removes only Clang's `nocapture` parameter attribute (unsupported by this Alive2 front end), and asserts that the files otherwise match exactly. The bidirectional proof passes; an injected `+1` in the SIMD result yields a concrete value mismatch (`logs/simdjson-eight-digits-negative.log`). This local-kernel proof does not cover complete JSON parsing or establish a benchmark speedup.

`bash benchmarks/run_aws_lc_alive2.sh` compares the pinned `CRYPTO_load_u32_be` used by `sha256.c` with a bytewise big-endian expression, using four explicitly initialized input bytes. Clang 20 `-O1` folds the local array into shifts/OR plus `bswap` on the target side; the reference is shifts/OR in big-endian order. The IR differs and bidirectional Alive2 passes. An injected `+1` yields a concrete mismatch (`logs/aws-lc-sha-word-negative.log`). This is a value proof for the four initialized bytes. It does not model arbitrary caller memory, the complete SHA-256 compression function, or a measured optimization.
