# Task: Improve CompCert Code Layout Without Weakening Compiler Correctness

## Objective

Optimize the quality of code generated by **CompCert 3.18** by improving its basic-block layout / CFG linearization heuristic.

The baseline is the official CompCert `v3.18` release. Pin the exact source commit before beginning.

Your goal is **not primarily wall-clock speed**. Instead, improve the structural quality of generated code in a way that is:

1. semantically verified by CompCert's existing correctness infrastructure;
2. non-trivial and applicable to real programs;
3. general across programs rather than benchmark-specific;
4. explainable in terms of compiler/code-generation mechanisms.

The primary optimization target is:

> Given an LTL control-flow graph, choose a better ordering of reachable basic blocks so that desirable control-flow edges become fall-through edges, reducing unnecessary explicit jumps and improving code layout.

Possible mechanisms include, but are not limited to:

- successor-chain / trace-based block placement;
- loop-aware block placement;
- preferring likely continuation edges over exits;
- arranging conditional successors to favor fall-through;
- keeping related blocks contiguous;
- reducing unnecessary control-flow transfers;
- improving local code layout in ways plausibly beneficial for instruction-cache locality.

Do not optimize benchmark source code itself.

---

# Scope of Modification

The intended primary modification point is:

```text
backend/Linearizeaux.ml
```

in particular the implementation corresponding to:

```text
Linearize.enumerate_aux
```

You may add small helper modules/functions used solely by the layout heuristic.

You MAY NOT modify:

```text
backend/Linearize.v
backend/Linearizeproof.v
driver/Compiler.v
```

or any Rocq/Coq theorem, semantic definition, correctness checker, validator, or proof used to establish compiler correctness.

You must also not modify:

- benchmark source programs;
- the LTL semantics;
- the Linear semantics;
- the existing enumeration validator;
- the definition of reachable blocks;
- the compiler correctness theorem;
- the extraction mapping in a way that weakens the verification boundary.

Do not use:

- `Admitted`;
- `admit`;
- new axioms;
- `Obj.magic`;
- unsafe casts;
- FFI tricks that bypass the verified representation;
- benchmark-name-specific rules;
- source-file-name-specific rules;
- hard-coded outputs for individual programs.

The optimized heuristic should still simply compute an ordering of CFG nodes.

---

# Correctness Requirement

Correctness is a **hard gate**. An optimization that improves code quality but weakens or bypasses verification is invalid.

## Existing CompCert verification boundary

CompCert deliberately separates block-order selection from verified linearization.

Conceptually:

```text
LTL CFG
   |
   v
untrusted enumerate_aux
   |
   v
candidate list of CFG nodes
   |
   v
verified enumeration checker
   |
   v
verified LTL -> Linear transformation
   |
   v
existing semantic-preservation theorem
```

`enumerate_aux` itself is allowed to be untrusted.

The existing Rocq code checks that the returned enumeration is valid, in particular that reachable nodes are represented without duplicates and that all required reachable nodes occur.

The verified linearization pass then transforms LTL into Linear code using this enumeration.

Therefore, you should improve the heuristic **without modifying the checker or proof**.

---

# What Must Be Proved

Do NOT attempt to prove:

```text
baseline_assembly = optimized_assembly
```

The optimized assembly is intentionally allowed to differ from the baseline.

Instead, retain the existing CompCert semantic-preservation theorem.

At the linearization level, the required property is the existing semantic preservation result for:

```text
LTL -> Linear
```

through `Linearizeproof`.

At the whole-compiler level, the final compiler must continue to satisfy CompCert's existing theorem of the form:

```text
forall p tp,
  transf_c_program p = OK tp ->
  backward_simulation
    (Csem.semantics p)
    (Asm.semantics tp).
```

In other words:

```text
source program P
      |
      +------ baseline compiler ------> A_baseline
      |
      +------ modified compiler ------> A_optimized
```

Both compiler outputs must remain connected to the same source semantics through CompCert's verified compiler theorem.

For well-defined benchmark programs with deterministic observable behavior, this implies that both generated programs preserve the intended observable source behavior.

Do not claim that the two assembly files are identical or directly bisimilar unless you separately prove such a statement.

---

# Proof / Verification Acceptance Criteria

The optimized compiler is considered verified only if ALL of the following hold.

### 1. Existing Rocq proofs remain unchanged

No weakening or modification of:

```text
Linearize.v
Linearizeproof.v
Compiler.v
```

or other semantic-preservation proofs.

### 2. Full verified CompCert build succeeds

Rebuild CompCert from a clean checkout/environment.

All relevant Rocq proof files must compile successfully.

In particular, the existing linearization proof and whole-compiler correctness theorem must still be part of the successfully built compiler.

### 3. Every generated enumeration passes the original checker

You may not circumvent validation.

If the new heuristic produces an invalid enumeration, compilation should fail through the existing mechanism rather than silently accepting it.

### 4. No loss of compiler applicability

For every evaluation program successfully compiled by baseline CompCert:

```text
baseline compiles P
```

the modified compiler must also successfully compile `P`.

The optimization must not improve its score by rejecting difficult programs.

Crashes, exceptions, infinite loops in the heuristic, and validator failures count as failures.

### 5. Functional integration tests still pass

Run the generated executables and verify benchmark-provided expected outputs/checksums where available.

These runtime tests are integration checks, not substitutes for the formal proof.

# Optimization Metrics

Wall-clock runtime is NOT the primary objective.

Evaluate structural code quality first.

## Primary Metric A: Fall-through quality

Measure how many eligible CFG transfers are realized as fall-through edges after linearization.

For each function record:

```text
eligible control-flow edges
fall-through edges
explicit control-flow transfers introduced by layout
```

Report:

```text
fallthrough_rate =
    fallthrough_edges / eligible_edges
```

Higher is better.

---

## Primary Metric B: Explicit unconditional jumps

Count explicit unconditional jumps introduced in generated Linear code.

For each benchmark report:

```text
baseline_Lgoto_count
optimized_Lgoto_count
relative_change
```

Lower is better.

The evaluator should obtain this from the Linear intermediate representation rather than inferring it exclusively from final architecture-specific assembly.

---

## Primary Metric C: Generated code size

Measure executable code size, especially:

```text
.text
```

using identical compilation and linking settings.

Report:

```text
optimized_text_size / baseline_text_size
```

Lower is better.

Do not trade an arbitrarily large increase in code size for a tiny reduction in jumps.

---

# Secondary Metrics

These are diagnostic metrics and should not determine whether the optimization is valid.

Where reliable hardware measurement is available, report:

```text
instructions
branches
branch-misses
cycles
wall-clock time
```

using identical machine, input and compiler settings.

Do not require a fixed runtime improvement such as 2x.

A meaningful structural improvement with little measurable runtime change is still a valid research result.

Likewise, report regressions rather than hiding them.

# Benchmark Suites

Use four evaluation tiers.

## Tier 0 — CompCert Regression / Applicability Suite

Use the C programs shipped with CompCert, especially:

```text
test/c
```

Purpose:

- compiler regression testing;
- compilation-success testing;
- functional sanity checking;
- finding unusual CFG structures.

These tests are a correctness gate, not the primary optimization score.

The modified compiler must not lose support for programs accepted by the baseline.

---

## Tier 1 — Embench-IoT

Use the stable **Embench-IoT** benchmark suite.

Use all workloads that can be compiled successfully by unmodified CompCert 3.18 under the frozen benchmark harness.

Before any optimization work:

1. compile every workload with baseline CompCert;
2. record the baseline-supported subset;
3. freeze that subset;
4. use exactly the same subset for all candidate compilers.

Embench should be the primary visible development benchmark.

It is particularly useful because it consists of small real-world embedded workloads and explicitly supports both code-size and execution-efficiency evaluation.

Report per-benchmark and aggregate:

```text
fallthrough rate
Lgoto count
.text size
optional dynamic counters
```

Do not optimize only the aggregate score; report the full distribution.

---

## Tier 2 — MiBench

Use the **MiBench** benchmark suite as the main real-world holdout evaluation.

CompCert itself has historically/currently used MiBench when evaluating generated-code performance, making it especially relevant.

Again:

1. determine the subset accepted by pristine CompCert 3.18;
2. freeze that subset before candidate evaluation;
3. require every candidate to compile every baseline-supported workload.

Use project-level separation from the development suite.

Do not inspect benchmark names in the optimization heuristic.

MiBench is the primary generalization test.

---

## Tier 3 — PolyBench/C

Use **PolyBench/C 4.2.1** as a contrasting / negative-control suite.

PolyBench contains numerical and loop-heavy kernels.

The goal is not necessarily to obtain large improvements here.

Instead ask:

- Does the layout optimization generalize to regular numerical CFGs?
- Does it introduce regressions?
- Does it reveal that basic-block layout is not the limiting optimization for these workloads?

Report PolyBench separately from Embench and MiBench.

Do not average all suites into a single number that obscures these differences.

---

Use the following conceptual split:

    PolyBench/C

# Aggregate Reporting

For count/size ratios, use geometric means where appropriate.

Always provide per-program results as well.

For each benchmark `i`, report ratios such as:

```text
R_jump(i) =
    (1 + jumps_baseline(i))
    /
    (1 + jumps_optimized(i))

R_size(i) =
    text_size_baseline(i)
    /
    text_size_optimized(i)
```

A value greater than 1 indicates improvement.

Do NOT collapse correctness into this score.

Correctness is binary and must pass before optimization metrics are considered.

---

# Success Criteria

A candidate solution is successful only if:

1. all formal correctness gates pass;
2. no existing semantic proof or validator is weakened;
3. all baseline-supported evaluation programs still compile;
4. functional benchmark checks pass;
5. the optimization is program-general, not benchmark-specific;
6. it produces a reproducible improvement in at least one primary structural metric on held-out real-world programs;
7. it does not create disproportionate regressions in other primary metrics;
8. the mechanism responsible for the improvement is identified and explained.

There is **no required wall-clock speedup threshold**.

A non-trivial improvement in generated control-flow layout that survives the verified CompCert pipeline and generalizes to held-out programs satisfies the central task objective.
