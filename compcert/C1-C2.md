# Follow-up protocol: C1 layout and C2 CFG changes

This supersedes the v2 acceptance block under the user's follow-up instruction.
The prior v2 sources, raw runs, proof logs and historical reports are retained.

## Acceptance

MiBench compilation coverage remains 12/12. Functional acceptance is defined
by pristine baseline evidence: all 11 baseline-valid executables must pass.
The invalid `bf` workload remains in compilation coverage and structural
tables, with its raw runtime failures and source-definedness limitation shown.
The separate upstream `bftest` known-answer tests remain mandatory. No
benchmark-source repair or candidate-dependent exclusion is allowed.

## C1: search beyond baseline groups

Implement three node-level policies: greedy trace construction, multistart
unweighted search, and multistart loop-weighted search. Baseline group
boundaries are not constraints; the baseline permutation may be an incumbent.
Search includes single-node relocation, node swaps, subsequence relocation,
bounded directed reversals, and temporary neutral moves. Preserve the best
observed complete permutation. A weighted variant uses static cyclic-SCC edge
weights, not measured execution frequencies. Retain unchanged original
validation and semantic-preservation proofs.

Develop on Embench and test/c only. Freeze all implementations before a single
MiBench comparison. MiBench has already been observed, so label the new result
as confirmation on a previously observed suite, not a fresh unseen holdout.
Do not tune after viewing its per-program results. Retain PolyBench as the
separate numerical control. If broader search still yields modest gains,
report that empirical limitation and proceed to C2; do not keep tuning v2.
Neither heuristic convergence nor a small measured gain proves a global
optimum or an upper bound on possible layout improvement.

## C2: tail duplication / block cloning

Build an isolated research case that changes the CFG. Repeating an existing
node ID in the enumeration is rejected by the existing checker. Fresh-ID
cloning instead changes fn_code and redirects incoming edges; this requires
an additional source-CFG to cloned-CFG semantic-preservation argument.
Checking an enumeration of the cloned CFG alone does not establish that
argument. Keep the production verified compiler boundary intact and clearly
label any transformation without that additional proof as experimental.
Measure benefits and code growth, and report exactly what a stronger checker
or new pass proof must establish. Existing semantic definitions/proofs must
not be weakened to make the experiment pass.
