You are working on a verified CUDA optimization task.

Your goal is to optimize a specific production CUDA kernel for performance while obtaining a machine-checkable functional-equivalence result between the original and optimized PTX using Volta.

This is not merely a benchmarking task.

A candidate optimization is successful only if:

1. it is integrated into the real repository;
2. it measurably improves a meaningful GPU-performance metric;
3. the original and optimized kernels both compile to PTX under the same toolchain and flags;
4. Volta proves the relevant outputs equivalent;
5. Volta reports no race or deadlock introduced by the optimization;
6. normal repository correctness tests still pass.

Do not weaken verification to make an optimization pass.

# Critical correctness rule

Do NOT consider ordinary tests to be the equivalence proof.

The proof gate must be:

```text
original CUDA
      ↓ same nvcc configuration
reference PTX
      │
      │
      ├──────────┐
      │          │
optimized CUDA   │
      ↓          │
optimized PTX    │
      │          │
      └── Volta compare
                 ↓
          proved equivalent
```

Use the public Volta implementation corresponding to:

```text
https://github.com/willtunnels/volta
```

Pin its exact commit in the experiment log.

# Important semantic qualification

Volta's functional-equivalence model treats floating-point values as real numbers.

Therefore, do not describe a successful Volta result as:

```text
bit-exact IEEE-754 equivalence
```

unless an independent bit-exact proof exists.

The formal claim for this task is:

```text
equivalent under Volta's supported PTX / real-valued semantic model
```

In addition, perform actual floating-point differential tests on GPU and report:

```text
maximum absolute error
maximum relative error
maximum ULP difference when practical
```

using the repository's accepted numerical tolerance.

Do not introduce lower precision, fast approximations, or relaxed numerical semantics merely to improve performance unless explicitly studied as a separate experiment.

---

# Verification integrity rules

You MAY NOT:

- modify Volta's semantics to make the candidate pass;
- remove output arrays from the comparison merely because they disagree;
- compare only a convenient subset of outputs when the remaining outputs are part of the kernel contract;
- replace formal equivalence with random testing;
- reduce the valid input domain without recording it;
- hard-code benchmark inputs;
- specialize the optimized implementation to secret benchmark values;
- alter the reference PTX;
- change compilation flags between baseline and candidate;
- suppress race/deadlock findings;
- silently accept `unknown`, `unsupported`, timeout, parse failure, or partial verification as proof success.

A Volta result counts as VERIFIED only when the requested complete output footprint is successfully proven equivalent.

Record the exact Volta command and stdout/stderr.

# Phase 1 — Baseline reconstruction

Before modifying anything:

1. build the repository cleanly;
2. locate the actual kernel instantiation and launch path;
3. create a minimal reproducible kernel benchmark;
4. determine the exact template specialization;
5. generate baseline PTX;
6. establish a working Volta invocation;
7. make Volta compare the baseline PTX against itself.

Self-equivalence must succeed before optimization work begins.

If baseline self-equivalence fails, stop optimization work and classify the reason:

```text
PTX parser limitation
unsupported instruction
unsupported synchronization primitive
data-dependent memory address
dynamic control-flow limitation
unsupported mathematical operator
unsupported launch structure
tool bug
incorrect harness
```

Do NOT patch around this invisibly.

Write the finding down.

# Phase 5 — Iterative verified optimization

For each candidate:

1. implement the optimization;
2. compile it;
3. run repository tests;
4. generate PTX using exactly the same configuration as the baseline;
5. run Volta;
6. only if proof succeeds, benchmark performance;
7. retain the candidate if it improves the Pareto frontier.

Use the loop:

```text
proposal
  ↓
compile
  ↓
tests
  ↓
PTX
  ↓
Volta
  ↓
verified?
  ├── no → classify failure and revise
  └── yes
        ↓
     benchmark
        ↓
     keep / reject
```

Do not wait until the end to run verification.

The verifier should be inside the optimization loop.

# Proof-failure taxonomy

Every failed candidate must be classified as one of:

```text
A. actual semantic inequivalence
B. introduced race
C. introduced deadlock
D. unsupported PTX instruction
E. unsupported synchronization feature
F. data-dependent control flow
G. data-dependent memory addressing
H. equivalent but outside Volta's decision procedure
I. verification timeout / scalability
J. compiler/harness/tooling issue
K. unknown
```

Preserve minimal reproductions of interesting D-I cases.

These are research results, not merely failed experiments.

---

# Do not automatically patch Volta

If a candidate looks semantically correct but Volta cannot verify it:

1. minimize the failing PTX feature;
2. determine whether the limitation is fundamental or implementation-specific;
3. record the optimization that triggered it;
4. continue searching for a verifiable alternative.

Only after the baseline study should you consider extending Volta.

Any Volta extension must be a separate commit and a separate experiment.

Never mix:

```text
kernel optimization
```

and

```text
verification-system modification
```

into one opaque patch.

# Performance benchmark protocol

Use the actual repository implementation, not only a stripped-down verification harness.

Use fixed representative problem sizes.

For each measurement:

- run sufficient warm-up iterations;
- use CUDA events or an equivalent GPU-side timing method;
- batch tiny kernels across repeated launches if necessary;
- report median;
- also report dispersion such as p5/p95 or standard deviation;
- run baseline and candidate interleaved when possible;
- use identical clocks, GPU state and build flags.

A reasonable initial protocol is:

```text
100-200 warmup launches
at least 1000 measured launches for small kernels
repeat the entire measurement 10-30 times
report median run
```

Do not require an arbitrary target such as 2x.

Even a moderate improvement is useful if the mechanism is nontrivial and the proof is strong.
