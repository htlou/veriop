# Aeneas feasibility and optimization pilot

**The best measured base64 candidate reaches 2.034× across eight selected official workloads in four rounds and now has a complete extracted public `encode_slice` equivalence proof, including padding, errors, and the complete returned buffer. Individual workload gains range from 1.836× to 2.758×. LZ4 has no repeatable speedup or full block proof. The combined goal is not complete.**

This experiment implements the attached proposal using the acceptance criteria in `../docs/project_doc.md` and the accompanying paper. Rust is translated through Charon and Aeneas; the original generated function is the specification. Native timing uses the upstream benchmarks. No repository-specific semantic models were written.

| Target | Charon | Generated Lean checks | Equality proof | Decision |
|---|---|---|---|---|
| base64 `encode_scalar_tail`, including its dependency and loops | Pass | Pass | Pass, eight declaration equalities | Go for this helper |
| LZ4 `token_from_literal` | Pass | Pass | Pass, arithmetic branch rewrite | Go for this helper |
| LZ4 `compress_into` | Pass | Fails | Unavailable | No-go on this pin |
| LZ4 `decompress_into` | Pass | Fails | Unavailable | No-go on this pin |
| Strict declaration-wise equality for LZ4's block module | Pass | Fails | Unavailable | No-go on this pin |
| Base64 `internal_encode`, baseline and measured pair-table candidate | Pass with partial monomorphization | Pass with local translator fixes | Complete function equality, matching tables, all input/output slices | Public `encode_slice` now proved for the pairs-tail candidate; see the latest evidence below |

The Charon nightly release initially downloaded emitted LLBC v0.1.276, while the Aeneas release requires v0.1.279. Building Charon from Aeneas's exact `charon-pin` resolved this mismatch. The successful setup is reproducible with [setup.sh](setup.sh); [logs/setup-replay.log](logs/setup-replay.log) records a completed replay.

The accepted base64 patch reverses `last_fast_index > 0` to `0 < last_fast_index` and adds `#[inline(always)]` to the private scalar helper. Both complete bodies were independently extracted from their real crate worktrees. Aeneas's `-loops-to-rec` generated three recursive loop functions. [Proofs.lean](proof/Proofs.lean) proves equality of the top-level helper, all three loops, `read_u64`, and all three local constants. The equality includes every argument, the returned output slice and byte count, and failure/divergence in the Aeneas model. There are no input-size bounds or success-only preconditions.

The LZ4 proof changes `lit_len < 15` to `lit_len <= 14` in its private literal-token helper and proves equality for every `usize` input. The nine successful theorems are recorded in [logs/verify-lean.log](logs/verify-lean.log). Those initial proofs cover comparison reordering and inlining. The later pair-table and remainder-loop proofs described below cover algorithm-changing rewrites.

The proof audit finds Lean's `propext`, `Classical.choice`, and `Quot.sound`, plus Aeneas's existing opaque **type** `core.fmt.Formatter` for base64's `unwrap` dependency. The successful proofs have no `sorryAx`, assumed equality lemmas, or native-decide/compiler-trust proof substitutions. The later concrete public-API proof also lists unused opaque decoder declarations carried by the concrete `Engine` record; its exact dependencies are recorded below. The translator, upstream Rust models, and Rust compiler remain trusted. Aeneas represents panic by a failure value; panic payloads and mutable state observable after catching a Rust unwind are outside the equality recorded here. Extraction retains checked arithmetic, while native benchmarks use the upstream release profiles; release-overflow behavior is not separately certified. These are model-level Tier 1 proofs with a trusted translation, not a verified Rust compiler pipeline.

[check-negative.sh](check-negative.sh) additionally checks that the same equality tactic rejects a Rust mutation that returns zero for every literal length. Its generated model is separate from the accepted candidates. See [logs/negative-rejection.log](logs/negative-rejection.log).

The larger translation probes identify concrete blockers:

- **LZ4 compression:** `compress_internal` uses `continue` to an outer loop, which Aeneas rejects. The API/module probes also request models for iterator adapters, native-endian conversion, trailing-zero counting, slice copying, and other standard-library operations. The generated templates include the rejected compression body as an axiom placeholder. They are retained as failed artifacts, never admitted to the successful proof build.
- **LZ4 decompression:** symbolic execution fails in `fastcpy::slice_copy` with `Unexpected result: Cps.Unit`. Generated templates additionally request `RangeBounds` methods and `slice::copy_within`.
- **LZ4 boolean helper:** `does_token_fit` emits `ok (¬ b)` where Lean expects `Bool`, causing a type error. This failed De Morgan experiment is preserved in `results/Lz4BoolNegation/`.
- **Base64 engine caller:** the generic `FnOnce` model and its mutable-slice closure disagree on the returned state tuple. Full monomorphization instead triggers an Aeneas internal error in its array-default preprocessing. The selected private helper avoids this problem without changing its source semantics.

Evidence is in [logs/lz4-aeneas-apis.log](logs/lz4-aeneas-apis.log), [logs/lz4-aeneas-decompress.log](logs/lz4-aeneas-decompress.log), [logs/lz4-aeneas-block.log](logs/lz4-aeneas-block.log), and [results/Base64Api/compile.log](results/Base64Api/compile.log). These failures establish the no-go result for the requested full LZ4 progression; the successful small helper is not evidence of full-module coverage.

Native features are fixed to `--no-default-features --features std` for base64 and `--no-default-features --features std,safe-encode,safe-decode,checked-decode` for LZ4. Base64's baseline, verified candidate, and both unrolling experiments each pass all **243** upstream tests, including documentation tests. LZ4's baseline and accepted helper rewrite each pass **57** block unit/integration tests, with one upstream test ignored. Plain `cargo test` also runs two frame documentation examples that fail because `frame` is disabled; their failures are preserved in `logs/lz4-baseline-tests.log`.

The unchanged base64 baseline ran all **88** upstream Criterion cases, covering encoding, decoding, buffer reuse, slice APIs, streams, and sizes from 3 bytes to 30 MiB. Optimization measurements then used all eight upstream `encode_slice` sizes. Four binaries ran in forward order and then reverse order on CPU 2, with independent Criterion result directories, 100 samples per case, and the upstream 0.5-second warmup / 3-second measurement settings. [results/machine.json](results/machine.json) records hardware and binary hashes; [results/performance.json](results/performance.json) includes per-round estimates and confidence intervals.

| Experiment | Proof status | Geometric-mean speedup, eight sizes | Observed per-size range |
|---|---|---:|---:|
| Helper inlining + comparison reversal | Checked | **0.999×** | 0.960–1.138× |
| Two-block scalar unrolling | Tests only | 0.911× | 0.745–0.974× |
| Eight-block scalar unrolling | Tests only | 0.993× | 0.746–1.185× |

Speedup is baseline latency divided by candidate latency, using the median of the two Criterion medians for each size. The aggregate weights the eight sizes equally. Upstream random input generation is retained, so each process draws its own input bytes. The machine is shared, and the two rounds sometimes disagree substantially; individual small gains are not a stable speedup claim. None of these experiments approaches 2×. Additional caller-inlining measurements are preserved in `logs/*paired-*.log`; that candidate also failed the caller-level translation check. No candidate is promoted as a performance improvement.

The LZ4 block benchmark uses its six existing datasets and upstream Binggan harness. [bench-lz4.sh](bench-lz4.sh) records compression and decompression timings for the baseline and proved helper rewrite in forward/reverse order, without enabling frame support. The observed geometric means are **0.856× compression** and **1.031× decompression**, with substantial timing variation; the patch changes only the compression helper. The 48 result records and [results/lz4-performance.json](results/lz4-performance.json) support no 2× improvement. Full block equivalence remains blocked by the translation failures above.

For this project, Aeneas is a workable route for selected ordinary Rust helpers with supported dependencies. Expanding the benchmark to complete compression modules first requires translator and shared-library-model improvements. Those costs should be measured as tool coverage work rather than hidden inside per-task semantic models.

**Complete base64 internal-encoder proof.** [Base64FastStepProof.lean](proof/Base64FastStepProof.lean) now proves `internal_encode_equiv` between the actual baseline and measured `base64-pairs-callchain` definitions. The engines may have arbitrary other fields; their encoding tables must match. The input and initial output slices are arbitrary. The theorem compares the entire `Result (Usize × Slice U8)`, including all output bytes, checked-arithmetic/slice failures, and divergence in the extracted model. It does not assume valid input indices or sufficient output capacity in the supporting scalar-tail/fast-loop equalities.

The proof regenerates the Rust functions using Aeneas's `-loops-no-rec` mode, which exposes each loop body and expresses repetition through the standard `loop` combinator. It proves table initialization, all 32 writes in a fast iteration, short-buffer and overflow cases, and then lifts body equality to the entire fast loop. An independently checked comparison specification connects standard-alphabet dispatch to that loop proof; unchanged scalar loops and wrapper structure complete the `internal_encode` equality. Generated files are never hand-edited. The previous recursive models and their narrower proofs remain available as historical evidence.

**Four-round base64 result above 2×.** The `base64-pairs-unroll8-exact` candidate doubles the fast loop from four to eight six-byte groups and admits an exactly full 50-byte input window. The first version retained the old `last_fast_index > 0` guard, which sent exactly 50 bytes through the slower remainder loop; it measured [1.900725555×](results/pairs-unroll8/performance.json). Correcting that boundary produces [2.034483115×](results/pairs-unroll8-exact/performance.json) over four counterbalanced rounds of the unchanged official Criterion workloads on CPU 2. The round aggregates are 2.023×, 2.046×, 2.005×, and 2.075×. Individual workload speedups range from 1.836× to 2.758×; this is an aggregate result, not a 2× gain on every size.
