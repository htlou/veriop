# llama.cpp `5a460dea`: GDN snapshot-copy fusion with a later consumer

**Verdict: scoped `NOT_EQUIV`.** The new CUDA fusion writes GDN snapshots directly into a cache and skips the following `CPY`. Its guard checks that the GDN tensor is not itself flagged as an output, but does not check whether a later node reads the GDN snapshot tail. The old kernel writes that tail; the fused kernel writes only the cache. A graph can therefore contain `GDN → tail view → CPY into cache → ADD(CPY result, tail view)`. For one token with `S_v=16`, `H=1`, `n_seqs=1`, `K=2`, initial state ones, zero `k`, `g`, and `v`, the snapshot is `1`. If the prior tail memory is zero, the old ADD result is `2` and the fused result is `1`.

Run `python3 -B history-eq/gpu/llama.cpp/5a460dea/reproduce.py` from the project root. It locks all three historical changed blobs, the unchanged `ggml.c` graph APIs, and the archived [diff](../source-screening/5a460dea.source.diff). It compiles and runs the **exact extracted fusion guard** against the described graph: the [native log](guard-native.log) confirms that it skips `CPY` while the later tail consumer remains. [Alive2](alive-old_to_new.log) then refutes both directions of the source-mapped observable ADD result; the [reverse log](alive-new_to_old.log) also reports one incorrect transformation and zero errors. [result.json](result.json) records the witness and source/model hashes.

This demonstrates a missing-use condition in the fusion guard and a counterexample in the source-mapped graph semantics. It is not a CUDA device run or a proof about every graph schedule. No official before/after benchmark score was measured.
