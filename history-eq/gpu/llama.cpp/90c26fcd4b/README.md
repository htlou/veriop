# llama.cpp `90c26fcd4b` — Vulkan expert-row hoisting

**Verdict: `EQUIV_PARTIAL` for row-ID coverage in a four-row, two-expert model (`nei0 = nei1 = 2`).** This is not a proof of final matrix values or of all Vulkan executions. The model assumes the ID buffer is stable across the count and scatter passes, takes each row's expert ID as either 0 or 1, and allows every order in which four invocations can receive their shared-memory `atomicAdd` cursor tickets. Z3 proves the old and new expert counts agree (`expert-counts.log`: `unsat`), no two distinct rows occupy the same expert-table slot (`unique-slots.log`: `unsat`), and each slot lies within the appropriate expert interval (`expert-intervals.log`: `unsat`). Thus each valid row has one slot in its expert's interval. The host's fast-division parameters for `nei0 = 2` reproduce ordinary division on all four indices (`fastdiv-two.log`: `unsat`); 16-bit coordinate packing round-trips under the host guard (`packing.log`: `unsat`).

The new table does **not** preserve old row order: for expert IDs `[0,0,1,1]`, a legal cursor order `[1,0,2,3]` places row 1 before row 0 (`different-order.log`: `sat`). The matrix shaders use row IDs both to fetch inputs and to select output addresses, so this internal order difference alone does not establish a tensor-output difference. The old subgroup `load_row_ids` function remains byte-identical in the new source and is still selected when hoisting is disabled.

Run `python3 -B history-eq/gpu/llama.cpp/90c26fcd4b/reproduce.py` from the project root. The script checks snippets from both exact historical revisions before running the SMT queries. It does not model shader memory barriers, all matrix variants, floating-point arithmetic, compiled SPIR-V, or an official before/after benchmark score. Kuiper and Volta were not run on this Vulkan pair.
