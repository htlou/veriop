# RoaringBitmap `c1ea7f01`: `Container.iorNot` outside-range bit

**Fixed-sample verdict: `NOT_EQUIV` for the existing public `Container.iorNot(RunContainer,int)` path.** With an `ArrayContainer` containing only value `10`, an empty `RunContainer`, and exclusive `endOfRange = 5`, the parent returns a container of cardinality 5 **without** value 10. The child returns cardinality 6 **with** value 10. The parent intersects its OR result with `[0,5)`; the child performs in-place OR with the range-complement and leaves the receiver's existing out-of-range bit intact. Both results are valid executions, so this is an observable before/after difference, not a performance measurement.

[`run.py`](run.py) checks the [complete archived production diff](../source-screening/c1ea7f01.source.diff) against the historical Git objects. It compiles the exact parent/child `Container`, `ArrayContainer`, `RunContainer`, and `BitmapContainer` source blobs with the same local RoaringBitmap 1.6.24 jar providing missing unchanged dependencies, then runs the [same witness](Witness.java) against each classpath. The [result record](witness.json) contains every target blob ID, the fallback jar hash, and the output. Reproduce with `python3 history-eq/java/RoaringBitmap/c1ea7f01/run.py` from the project root.

The counterexample concerns this public container method; the larger `RoaringBitmap.orNot` rewrite and other changed paths were not checked. KeY did not prove this pair. The fallback jar is not historical, but is identical in both runs and does not replace the four historical classes whose method calls produce the differing results. No official historical before/after benchmark score was measured.
