# RoaringBitmap historical optimization `684531c1`

Commit `684531c13877fbdacccf02262b32e6faf889d76f` adds a `rank(Character.MAX_VALUE)` cardinality fast path to six container classes. `source.diff` is the complete production-source diff. The exact pre/post `ArrayContainer.java` blobs are saved in `old/` and `new/`.

**Verdict: `EQUIV_PARTIAL` for well-formed `ArrayContainer.rank(0xFFFF)`; whole commit unverified.** The parent and child `ArrayContainer.java` Git blobs are `620a2c80225bc3adf7e4db8f07c5eb812be35225` and `91ca912414e20a066a91fce3dfadd0d6878fbfeb`. Their shared `Util.java` Git blob is `e776660700808df54a9835d850979bc365d5cf88`; it selects `hybridUnsignedBinarySearch`. In that exact source, the old rank calls the search with `begin=0`, `end=cardinality`, and `k=0xFFFF`, then converts a found index or negative insertion point to a count. The new rank returns `cardinality` immediately.

The [Z3 obligations](rank-max.smt2) check the source-mapped branches for `0 <= cardinality <= 65536` and distinct sorted `char` values. With an empty array or a final value below `0xFFFF`, the old search returns `-cardinality-1`. Otherwise the final value is `0xFFFF` and every earlier value is smaller: the binary loop always advances `low`, and the final sequential loop reaches the last slot and returns `cardinality-1`. In either case the old rank conversion yields `cardinality`, the new result. All seven negated obligations are `unsat` in the [solver log](rank-max-z3.log). This is a source-mapped mathematical proof of this method and invariant, not a direct KeY proof of the Java class. It does not cover malformed container state or the other five changed container classes.

KeY 3.0 was invoked on both historical `ArrayContainer.java` files. Both attempts stopped during source loading with `UnsolvedSymbolException: Container`, before creating a proof obligation ([old](old-key-direct.log), [new](new-key-direct.log)). A full KeY project with the class dependencies and contracts has not been built. Neither KeY outcome establishes that KeY inherently cannot support the change.

The existing pinned `Util.iterateUntil` KeY contract in `benchmarks/key/roaring_iterate/` concerns a different method and does not contribute to this verdict. The official JMH build/smoke results concern the pinned version; they are not a before/after measurement of `684531c1`.
