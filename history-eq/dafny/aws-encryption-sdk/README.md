For `79e1306`, the old and new recursive Dafny function bodies/specifications for `SerializableTypes.LinearLength`, `EncryptionContext.WriteAADPairs`, and `MessageBody.WriteMessageRegularFrames` are unchanged apart from the executable declaration form. The new `by method` implementations create additional verification obligations. All six targeted source checks ran on exact archived repository and MPL submodule revisions, with the unchanged `libraries` submodule revision. The old checks report `1 verified, 0 errors`; new checks report `2 verified, 0 errors`. These checks support **local Dafny implementation-to-spec refinement**, not whole-commit equivalence. The new `MessageBody.IsMessageRegularFramesCanBeSplit` lemma contains `assume {:axiom} MessageFramesAreMonotonic(accumulator)`, so the related MessageBody result depends on that unproved assumption. The commit also modifies Go runtime interop and Dafny TestVectors files, outside these six target obligations.

For `ffc1e2d`, the production runtime change is Go source. Dafny does not verify those Go conversion functions. The source diff establishes performance intent but neither equivalence nor a counterexample.

For `2ea5e47`, the application opts into an external runtime feature that replaces arbitrary-precision `DafnyInt` with an `i128`-backed implementation (the new Smithy-Dafny runtime's `small_int.rs` declares `type InternalInt = i128`). The old and new representations do not share the same unrestricted integer domain. The configured Aeneas harness does not compare Cargo feature selections or external runtime crates, and Dafny source verification does not compare the Rust representations. No Aeneas proof or counterexample is claimed. This is an unsupported whole-commit check, not a verified application-level mismatch.

For `dbe55d7`, `dbe55d7-zero-sequence.dfy` proves two exact expression rewrites used by `MessageBody.IVSeq` and the new `SerializableTypes.GetIvLengthZeros`: IVSeq for every 8-bit length at least 4 and every suffix byte sequence, and the zero sequence for every 8-bit length. It abstracts the unchanged `GetIvLength` and `UInt32ToSeq` results as inputs. Dafny 4.10 reports `8 verified, 0 errors`. The old and new historical `IVSeq` source both verify; the new `GetIvLengthZeros` source verifies. The old and new `LinearLength` source also verify, but no cross-version equivalence theorem covers its `nat` to `uint64` conversion or the other modified functions.

The [source-locked `Read` relation](dbe55d7-read-relation.dfy), rerunnable with `python3 -B history-eq/dafny/aws-encryption-sdk/verify_dbe55d7_read.py`, checks exact old/new `SerializeFunctions.Read` blob IDs and changed expressions before proving a Dafny projection of the result. Under `|buffer.bytes| < 2^64` and `buffer.start + length < 2^64`, the old natural-number end calculation and the new `uint64` `Add` calculation return the same success bytes and next position or the same `MoreNeeded` position. [The run log](dbe55d7-read-relation.log) reports `7 verified, 0 errors`. The projection models the unchanged `Need` helper as a success/failure branch and uses the exact `Add` body `x + y` under the explicit no-overflow bound. It does not import `MemoryMath`, prove behavior when the bound fails, compare all changed callers, or establish whole-commit equivalence. The whole optimization remains **UNKNOWN**.

The new MPL StandardLibrary revision adds `MemoryMath.ValueIsSafeBecauseItIsInMemory(value: nat)` as an axiom with no precondition and postcondition `value < 2^64`. `dbe55d7-memorymath-negative.dfy` invokes it at `2^64` and Dafny proves `false` (`1 verified, 0 errors`). Therefore any claim based on the new source's `MemoryMath`-dependent target checks must state the trusted memory-size assumption; the independent zero-sequence equivalence proof does not import that library. The contradiction check is a proof-trust diagnostic, **not** a counterexample showing the old and new SDK outputs differ.
