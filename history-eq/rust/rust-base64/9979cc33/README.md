# rust-base64 `9979cc33` — separate morsel bytes

**Verdict: `EQUIV` for runtime decoding through the historical `GeneralPurpose` and `Naive` callers.** The [reproduction](reproduce.py) locks the exact historical Rust source blobs and checks that both callers are unchanged. It proves with Z3 that, for every caller-reachable morsel count `0, 2, 3, 4, 6, 7, 8`, arbitrary decoded `u8` morsels, and zero-initialized unused array entries, the old incremental `u64` shifts equal the new eight fixed shifts. The old match-arm output length equals the new `count * 6 / 8 * 8` length for those counts. All [eight queries](result.json) are `unsat` for a difference.

The unchanged `GeneralPurpose` caller rejects lengths with remainder `1` or `5` modulo eight and passes at most eight trailing bytes. The unchanged `Naive` caller rejects remainder `1` modulo four and passes at most four. In either caller, padding after only one or five data symbols is rejected before the changed packing code; the reproduction enumerates all valid/padding/invalid byte-category shapes of those suffix lengths and confirms the reachable counts. For these counts, equal packed bits and output length give the same trailing-bit error, output writes, output bounds behavior, and returned metadata. The remaining input-validation and padding-error branches are textually unchanged and run before those calculations. The other changed file only removes `#![deny(warnings)]`, which does not change runtime decoding after a successful build.

This is an exact-source control-flow argument plus exhaustive finite-category checking and Z3 bit-vector proofs, **not** a full Aeneas/Lean translation: the historical [Aeneas attempt](../work/9979cc3/SufOld-aeneas.log) fails on both sides with “Could not match the contexts.” Z3 was invoked directly from a Kuiper installation; Kuiper itself did not check the pair. Build-warning policy, allocation, timing, and panic backtraces are outside this runtime observation. No official before/after benchmark score was measured.

The excluded counts matter. A [release-mode native witness](invalid-count-result.json) compiled the exact old/new `decode_suffix` bodies with the same minimal type harness: on one or five valid `A` characters, the old direct helper panics, while the new helper returns `Ok` with 0 or 3 bytes. The same script builds both complete historical crates and calls their public `STANDARD.decode`: **both return `InvalidLength`** on these inputs. This is a direct-helper counterexample outside the callers' reachable domain, not a public decode counterexample. Run `python3 -B history-eq/rust/rust-base64/9979cc33/check_invalid_count.py` to reproduce it.
